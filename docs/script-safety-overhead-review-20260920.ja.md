追記: 以下の4件は修正しました。変更内容と検証結果は[修正記録](script-overhead-fixes-20260920.ja.md)を参照してください。以下は修正前のレビュー記録です。

SHA-256撤去後のスクリプト機能を中心に、カタログ、実行前チェック、排他制御、出力捕捉、後処理、共通MCPの検証経路を確認しました。優先して見直す候補は2件、効果の小さい軽量化候補は2件です。製品コードと既存テストは変更していません。

## P2: MANIFEST.MFを含むルートの一律除外

箇所: `src/ghidra_mcp/application/services/script_catalog.py:362–378`

`META-INF/MANIFEST.MF` が存在するだけで `rejected_reason="manifest_present"` を設定し、そのルートのスクリプトをすべてカタログから除外します。依存関係をカタログが把握できないことを理由としていますが、現在の機能は運用者のスクリプトとクライアントの任意ソースを同じOS権限で実行します。依存するコードを制限するという保証はありません。

Ghidra 12.1.3の同梱ソースでも、`GhidraSourceBundle.build()` はソースのマニフェストを処理する分岐を持っています。実機では有効なマニフェストを持つJavaとPyGhidraのスクリプトを用意し、どちらもカタログには0件、`run_script(script_id=...)` は `SCRIPT_NOT_FOUND` になる一方、カタログ解決後の通常ランタイムへ同じファイルを渡すと成功することを確認しました。プロバイダーやファイル内容は変更していません。

推奨: ファイルが存在するという理由だけの除外を撤去し、Ghidraの通常のロード・コンパイル処理に任せる。無効なマニフェストや解決不能な依存は、その具体的な診断を返す。今回の確認は有効な最小マニフェスト2ケースであり、任意のOSGi構成が必ず動くという確認ではありません。

## P2: 変更のないスクリプトでも共有デコンパイラーを破棄

箇所: `src/ghidra_headless/handlers/commands/scripts.py:95–99`

後処理が常に `ctx.reset_decompiler()` を呼び、共有 `DecompInterface` を `dispose()` します。Ghidraの同梱ソースでは、この破棄によりデコンパイラープロセスも解放されます。

実機で、デコンパイラーを準備した後に `println()` だけのスクリプトを実行しました。3回とも `transaction_outcome=unchanged`、プログラムのrevisionも同一でしたが、共有インターフェースは破棄されました。その直前と直後に同じ関数をデコンパイルした時間は以下です。

| 試行 | 準備済みの共有インターフェース | 無変更スクリプトの直後 |
| --- | ---: | ---: |
| 1 | 132.24 ms | 356.37 ms |
| 2 | 124.07 ms | 342.10 ms |
| 3 | 116.74 ms | 344.03 ms |
| 中央値 | 124.07 ms | 344.03 ms |

推奨: 実行状態が正常でプログラムの変更もない場合は共有インターフェースを維持する。変更・ロールバック・実行状態不明の場合は引き続き適切に無効化する。インラインの一時バンドル除去など、ほかの後処理まで省略しない。上の数値は一つの関数・環境での測定で、全スクリプトの高速化率ではありません。

## P3: スレッドID収集のために全スタックを採取

箇所: `src/ghidra_headless/scripts/execution.py:83`、`:193`、`:250`

`Thread.getAllStackTraces()` で全スレッドのスタックを採取していますが、コードは返されたMapのキーであるThreadだけを使用し、スタック本体を参照していません。監視の前後と、残存スレッドを待つループでこの処理が走ります。

実機の60スレッド環境で、開始時のID集合取得を比較しました。現在の `snapshot_threads()` は1回の中央値0.331 ms、公開APIの `ThreadMXBean.getAllThreadIds()` によるID集合取得は0.033 msでした。いずれも5組×100回、事前ウォームアップありです。Java 21の同梱ソースで、このAPIに非推奨指定がないことも確認しました。

推奨: IDだけ必要な場所はIDを列挙し、新しく見つかったスレッドの名前などは必要時に取得する。残存スレッド検知自体は維持する。差は小さく、これは監視の一部分の比較です。検出後に必要となるThreadInfo取得を含めた全経路の高速化率ではありません。

## P3: 出力上限に達した後も捨てるバイト列をコピー

箇所: `src/ghidra_headless/scripts/capture.py:43–55`

保持上限64 KiBに達した後も、Java byte配列を確保し、ByteBufferからコピーし、Pythonのbytesへ変換してから全量を破棄しています。

満杯の捕捉バッファに8 KiBずつ渡す部分の比較では、現在の処理が1回7.89 µs、ByteBufferの位置を進めて破棄数を加算する試作が5.19 µsでした。各5組×1,000回で、事前ウォームアップありです。試作でも保持された64 KiBの内容と破棄バイト数は一致しました。

推奨: 残り保持容量が0なら、データの変換を省略して入力を消費し、破棄数を加算する。上限・カウンター・排他制御は維持する。これもPython側のwrite処理のみの比較で、Javaの文字列エンコードやスクリプト全体を含めた性能測定ではありません。

## 今回は削除を勧めない処理

- 起動時のPyGhidra例外伝播チェック: JVMごとに一度で、失敗を成功扱いしてコミットする問題の再発を検知する。Java/Jythonの親もPyGhidraの子を呼べるため、全言語への適用には理由がある。
- 共有Jythonインタープリター: 親の言語だけでは必要性を判定できない。子スクリプトの例外・出力の伝播に必要。
- トランザクション終了状態、未終了トランザクション、残存処理の確認と隔離: 同一JVMでプログラムを共有する設計における状態保護。
- プロセス全体のスクリプトバリアと待機上限: Pythonのモジュール状態やOSGi/Jythonの共有状態を保護する。
- `expected_revision` と共有プロジェクトのチェックアウト・競合確認: 利用者や別クライアントの編集の上書きを防ぐ。
- MCPの入出力検証: 公開MCP経路とPythonからの直接呼び出し、論理結果と構造化された送信結果を扱っている。重複する変換の整理余地はあるが、境界ごとの検証をそのまま消す根拠は得ていない。

スクリプト実行後の通常の `analyze_program(force=true)` が誤隔離される可能性も調べましたが、今回の実機ケースでは隔離されず、その後のコメント編集も成功しました。この経路は問題として挙げていません。
