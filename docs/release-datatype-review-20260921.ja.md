## P2: 明示offsetの構造体メンバーを末尾以降に配置できない

対象: `src/ghidra_headless/handlers/commands/mutating_data_types.py:39–40, 80–81`

`create_struct` と `add_struct_members` は、`offset` があると構造体を拡張せず `replaceAtOffset()` を呼びます。このAPIは既存サイズの外側を受け付けないため、既定の `size=0` では先頭の `offset=0` さえ失敗します。既存構造体の末尾への追加でも、offsetを省略すれば成功し、同じ位置を明示すると失敗します。

```json
{"name":"Layout","members":[{"name":"value","type":"int","offset":0}]}
```

上記の `create_struct` は `Offset 0 is beyond end of structure (0).` で失敗します。`size: 4` を指定した場合と、メンバーの `offset` を省略した場合は成功します。

| 操作 | 条件 | 結果 |
| --- | --- | --- |
| 作成 | size省略、offset省略 | 成功、intをoffset 0に配置 |
| 作成 | size=4、offset=0 | 成功 |
| 作成 | size省略、offset=0 / 16 | どちらも失敗 |
| 4バイト構造体へ追加 | offset省略 | 成功、次のintをoffset 4に配置 |
| 4バイト構造体へ追加 | offset=4 / 16 | どちらも失敗 |

バイナリ形式の既知のフィールド位置から構造体を組み立てる、という自然な入力で発生します。スキーマとツール説明は明示offsetを受け付けていますが、事前のサイズ確保は要求していません。

修正方針: 明示offsetとメンバー長から必要なサイズを確保してから配置する処理を、作成・追加の両方に適用します。公開APIの `growStructure()` と `replaceAtOffset()` を組み合わせ、offset 0と16のフィールドを20バイトの構造体へ配置できることを別の検証で確認しました。負のoffsetなどの不正入力は引き続き拒否し、既存メンバーの位置をずらさない実装にする必要があります。

## P2: 列挙値の一括置換がJSONのキー順に依存する

対象: `src/ghidra_headless/handlers/commands/mutating_data_types.py:318–322`

`set_enum_values` は、置換する名前を1件削除するたびに新しい値を追加します。Ghidraはその時点で残っている値から符号の有無を判定するため、置換前の別の値が一時的に残っているだけで、妥当な最終状態への更新が拒否されます。

次の1バイトenumを用意します。

```json
{"A":-1,"B":-2}
```

更新する `values` が `{"A":255,"B":1}` だと、Aを追加する時点でB=-2が残っており、範囲を `(-128, 127)` と判定して255を拒否します。同じ内容を `{"B":1,"A":255}` の順で送ると、最終状態 `A=255, B=1, isSigned=false` への更新が成功します。

JSONオブジェクトのキー順だけで成否が変わるため、クライアントのシリアライズ方法によって同じ更新を適用できなくなります。失敗時はトランザクションによって元の値へ戻ることを確認しており、部分更新が残る問題ではありません。

修正方針: 置換対象の既存名をすべて削除してから新しい値を追加し、変更対象外の値を含む最終状態の範囲制約を満たすようにします。公開APIの削除・追加だけで、上記の両方のキー順を成功させられることを別の検証で確認しました。
