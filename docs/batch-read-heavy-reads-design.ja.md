# batch_read のデコンパイル・ディスアセンブル対応案

2026-09-14。**設計案。ここに記載する拡張は未実装。**

## 方針

既存の `batch_read` に `decompile_function` と `disassemble` を追加する。同一ターゲット、入力順、全件事前検証、公開ツール制限、1回のターゲット／プロジェクトロック、revision検査、項目別の成功／失敗／未実行を維持する。並列実行や自動解析は追加しない。

現在のデコンパイラは既にプログラムごとの `DecompInterface` を再利用している。バッチで新たに減らせるのは主に呼び出し回数と付随処理であり、デコンパイル計算自体の高速化とは分けて評価する。

```json
{
  "target": "default",
  "timeout_seconds": 45,
  "max_output_chars": 12000,
  "requests": [
    {"id": "meta", "tool": "get_function", "arguments": {"address": "0x401000"}, "fields": ["entry", "name"]},
    {"id": "asm", "tool": "disassemble", "arguments": {"address": "0x401000", "limit": 100}, "fields": ["address", "mnemonic", "operands"]},
    {"id": "c", "tool": "decompile_function", "arguments": {"address": "0x401000", "timeout_seconds": 15}}
  ]
}
```

既に分かっている複数関数も同様に列挙する。前の結果から次の対象を決める依存関係は別の呼び出しで扱う。軽い照会を先に置けば、重い処理が予算を使い切る前に取得できる。サーバーは要求順を勝手に並べ替えない。

## 初期上限案

| 項目 | 案 |
| --- | --- |
| バッチ要求数 | 既存の最大20件を維持 |
| デコンパイル数 | 1バッチ最大5件。測定前の暫定値 |
| デコンパイル1件の時間 | 未指定時はバッチ内15秒、単独呼び出しは既存120秒を維持。常にバッチ残時間以下 |
| バッチ時間 | 既定10秒、最大60秒を維持。重い処理をまとめるときは例のように明示指定 |
| ページ行数 | xrefs・call edges・disassembleの要求limit合計で既存の最大2,000行を共有 |
| 初回応答 | 既存のツール応答上限2,048〜12,000文字を維持（contentとstructuredContentの合計） |

`decompile_function.arguments.timeout_seconds` は任意の追加引数とし、単独呼び出しとバッチの型を共有する。公開モデルの未指定値は `null` とし、上記の既定値を実行経路で解決する。これにより単独呼び出しの既定動作を変えない。入力指定値にも1〜120秒の上限を持たせる。

## デコンパイル実行

現在の `_decompile_function_object` は固定120秒と `ctx.monitor()` を渡している。内部に期限とキャンセル可能なmonitorを渡せるようにし、Ghidraのタイムアウトとmonitorの両方で停止を要求する。期限は外部引数に混ぜず、内部の実行コンテキストとして渡す。

Ghidraに渡す秒数は「項目の時間上限」と「バッチ残時間」の小さい方を基にする。整数秒への変換で0秒や切り上げによる意図しない延長を作らない。開始時点で残時間が1秒未満なら、その項目は `not_run` にする。ロック待機や初期化・停止処理もあるため、厳密な壁時計の応答期限を保証するとは説明しない。

タイムアウトなどはGhidraの結果状態から判定し、文字列メッセージの推測で分類しない。新しい項目エラーコードは `DECOMPILE_TIMEOUT`、`DECOMPILE_FAILED` などを設ける。失敗時には既存のデコンパイラ再初期化処理を使い、処理の終了を確認してから残時間内で次の項目へ進む。

デコンパイラを起動できない、停止を確認できない、セッションが変わった、予期しない内部障害が発生した場合は、個別エラーとして握りつぶして続行しない。明示的なキャンセルは後続処理を開始せず、revision不一致は既存どおりバッチ全体を失敗させる。

成功時の `data` は単独ツールと同じCソース文字列を維持する。オブジェクト用の `fields` はこのツールではスキーマで禁止し、全件事前検証の段階で拒否する。

## ディスアセンブル実行

既存の関数指定／範囲指定とアドレスseekによるページ継続を再利用する。関数bodyの非連続範囲を維持し、未定義バイトから命令を作成しない。`fields` は各命令行に適用し、program・revision・has_more・next_cursorを残す。

関数と範囲の排他、範囲指定に必要な引数、lengthなどの静的な検証を単独ツールと共有して、バッチの開始前に検証する。アドレス解決や実際の関数の存在確認は実行時の項目エラーとして扱う。

命令の走査・変換中にも内部期限とキャンセルを確認する。初版では期限途中でできた不完全なページを成功扱いせず、その項目を時間超過エラーにする。完了したページだけ既存のcursorを返す。通常の `limit` 境界による部分ページとは区別する。

deadlineやmonitorを `arguments` に挿入しない。これらをクエリfingerprintに含めると、次のバッチで残時間が変わるだけでcursorが無効になるため。公開された元のクエリだけで継続の同一性を判定する。

## 大きいC本文の取得

既存の「全項目を1つのJSONキャッシュに保存する」方式を維持する。ただし大きいC文字列を `/items` のJSON項目として取得するだけでは1項目超過になりやすいため、保存済みC本文を直接読む経路を同時に追加する。

`read_result` のテキストモードに、成功したデコンパイル項目の文字列だけを選ぶ `path="/items/N/data"` を追加する。`offset_chars`・`limit_chars` はJSON表記のエスケープ済み文字列ではなく、復号したC本文の文字位置として解釈する。既存の `path=""` の生テキスト取得は維持する。

```json
{
  "result_id": "バッチが返したID",
  "mode": "text",
  "path": "/items/2/data",
  "offset_chars": 0,
  "limit_chars": 4000
}
```

`search_result` にも同じ文字列選択を追加する。検索の継続カーソルはresult_id・path・検索条件に紐付け、別の関数本文に転用できないようにする。初版のpathはこの限定形式と既存の形式のみとし、汎用JSONPath評価機能は導入しない。

既存の項目位置索引を使って対象項目だけを復号する。抽出文字列を再利用する場合は保持メモリ予算に計上し、元エントリーと同時に破棄する。キャッシュ上限や追い出し時は既存同様に取得不可を明示し、デコンパイルを暗黙に再実行しない。

応答で省略されたC本文には `result_id` と上記pathを使う取得情報を付ける。短いC本文は `data` にそのまま収める。バッチの状態一覧やディスアセンブルのページ情報がC本文に押し出されないよう、管理情報を先に出力予算へ割り当てる。

## 実装箇所と受け入れ条件

- `contracts/batch_models.py` と独立したcore guardに2種類を追加。デコンパイルのfields禁止、最大件数、ページ合計の検証を加える。
- `core_helpers.py`、`read_only_decompile.py` に期限・monitor・型付き失敗を導入。単独呼び出しの既定120秒と戻り値は維持する。
- `query_support.py` と `analysis_queries.py` に内部期限確認を追加し、既存cursorを維持する。
- `tool_dispatcher.py` で文字列結果を辞書として投影しないようにし、disassembleをページ投影へ追加する。
- 結果取得・検索でC本文の選択、Unicode・改行・バックスラッシュの正確な再構成、pathに紐付く検索継続を検証する。
- 実Ghidraで単独結果との一致、共有デコンパイラの再利用、非連続body、cursor継続、途中編集による全体拒否を検証する。
- 制御したテストで、1件の時間超過後の残り時間に応じた続行／未実行、残時間1秒未満、停止失敗時の全体中止、キャッシュ拒否・追い出しを検証する。
- 同じ関数集合・同じ出力条件で、ツール呼び出し数、取得を含む総応答量、完了時間、ピークメモリ、ロック占有時間、成功率を比較する。既にクライアントが並列に要求を送っている場合も比較条件として明記する。

順序は、(1) disassemble追加、(2) decompileの時間制御・型付き失敗とC本文取得、(3) decompileのバッチ公開、(4)同条件比較、とする。重い処理を公開する時点で時間制御と本文取得を揃える。
